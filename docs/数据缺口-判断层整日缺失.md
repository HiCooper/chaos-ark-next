# 数据缺口：判断层「整日缺失」

日期：2026-10-18　　涉及：`engine/config.py:KNOWN_JUDGE_GAPS`、`engine/ark.py:_judge_calendar_gaps`

## 一、现象

2026-10-18 跑 `ark.py daily`，水位从 2026-10-14 直接跳到 **2026-10-16**，
2026-10-15（周四）整天不见了。查证后确认这不是"当天没出结论"，而是**这一天不在系统里**：

| 数据源 | 2026-10-15 |
|---|---|
| 申万行业指数（判断层，L0 `sw_index`） | **0 / 120 只**有数据 |
| 全池 ETF（结算层，L0 `etf`） | 120 / 123 只有数据 |
| 上证指数（新股，L0 `bench`） | 有，收盘 3707.476（10-14 为 3767.227，10-16 为 3716.284） |

直接问源端也一样：`ak.index_hist_sw(symbol='801010')` 返回的最后几行是
`10-12 / 10-13 / 10-14 / 10-16`——**申万自己的接口就没有 10-15 这一根 bar**。

结论：市场当天开市（ETF 与指数都在交易），只是**申万行业指数当天整日无数据**。

## 二、为什么这是"静默"故障

系统里没有一处会报错：

- `panel.dates` 由行业指数的日期并集生成 → 没有这一天，于是 **没有 day 文件、没有结论**；
- 前端交易日历（`history.json`）也就没有这一格——看上去像"当日没出结论"，而不是"当日缺失"；
- 结算层按 `panel` 交易日计数（`end = buy_i + H`），所以**到期日整体少算一天**；
- `ark.py status` / `verify` 原本只检查"各层最后一天是否同日"，中间的空洞完全看不见；
- 兜底机制（`fill_realtime_tail`）只补**尾部**（`d > official_last`），对这种"中间洞"无能为力
  ——当 10-16 的官方数据到手后，`official_last` 已经是 10-16，10-15 永远不会被补。

## 三、审计：一共几个洞

判据：基准（新浪，最全）该日是交易日、`panel` 里没有 → 判断层整日缺失。
再核对 ETF 当日覆盖率，确认市场确实开市。

| 日期 | 申万 | ETF 覆盖 | 上证指数 | 位置 |
|---|---|---|---|---|

| 2015-09-02 | 0/120 | 24/123 | 有 | 同上 |
| 2022-03-03 | 0/120 | 102/123 | 有 | **回测内** |
| 2022-03-23 | 0/120 | 104/123 | 有 | 回测内 |
| 2022-03-31 | 0/120 | 104/123 | 有 | 回测内 |

不在本守卫的判定范围内。

## 四、处理策略

### 第一阶段（2026-10-18）：先加守卫，暂不补数据

1. **守卫**（已实现）：`ark.py` 新增 `_judge_calendar_gaps()`，以「基准交易日 − panel 日期」计算缺口。
   - `ark.py status`：逐个列出，附登记说明；
   - `ark.py verify`：**未登记的缺口一律失败**；已登记的通过；
   - `ark.py daily`：每次更新末尾自查，新洞打印 ⚠。
2. **登记**：经核对的已知空洞写进 `engine/config.py:KNOWN_JUDGE_GAPS`（含证据与不补的理由）。
   未登记的洞 = 新问题，必须核对后"补数据"或"登记"，二者必居其一。
3. **暂不补数据**的理由：源端常会 T+1~T+2 补发（10-15 的 bar 可能自己出现）；
   补数据本身是**口径变更**（见下节），需要单独批准并全量重放。

### 第二阶段（2026-10-20）：10-15 用 ETF 收益代理补齐

10-20 复查：申万已经把 **10-16、10-19 都出了**，唯独 10-15 仍 0/120（直接查源端接口确认），
判定为永久缺失 → 批准补齐。

实现：`engine/datasource_sw.py:fill_interior_holes()`，在 `build_panel` 里、**交易日轴之前**调用。
- 只补 `config.GAP_FILL_DATES` 里**逐个批准**的日期（现在是 `("2026-10-15",)`）；
  其余 9 个历史缺口继续按「已登记空洞」跳过——补历史会改回测，必须单独批准。
- 补法与尾部兜底同一口径：**只补收益、不发明点位**，
  `行业指数 10-15 收盘 = 该指数上一个官方收盘 × (1 + 对应 ETF 当日收益)`；
  101 个行业取到 ETF 收益，19 个无对应 ETF 的走当日横截面中位收益。
- 逐行打 `est = [gap_close_proxy | gap_close_xs_median, open, high, low, volume, amount]`、
  `src = etf_proxy_gap`；L0 用 `overwrite_est=True` 写入，申万补发即自动覆盖。
- 对齐体检：代理行业中位涨跌 **−2.30%** vs 基准（沪深300 −1.23% / 上证 −1.59% / 创业板 −2.92%），
  差 1.07pp < 5%，通过。

**补齐后必须重建结算层日历**：`etf_panel.dates` 直接取自 `panel.dates`，
不重建就会少了 10-15（结算层与判断层错位一天）。已一并加守卫，见下。

10-15 当天没有成交事件（当日只有 1 条埋伏结论，账户满仓），所以账本重放偏差、现金下限均不变。

#### 新增守卫：两层日历必须同日

`etf_panel.dates = panel.dates`（`build_etf_panel.py`），所以「判断层补了一天、结算层没重建」
会让结算层少一天——表现为我的持仓的「下一交易日」跨过那天、与结论日历对不上，
而水位检查只比最后一天，看不出来。`ark.py verify` 现已加上：

```
[verify] 判断层 / 结算层交易日集合一致 ...
  ✓ 两层同日历：6482 个交易日
```

负向实测：从 `etf_panel.dates` 里删掉 10-15 → `exit 1`，报「只在判断层：['2026-10-15']」。

## 五、如果以后还要补：两条口径路线

补数据必须**只补收益、不发明点位**，且逐条标 `est`，官方出数后由 `rawstore.put(overwrite_est=True)`
自动覆盖（与尾部兜底同一套机制）：

| 路线 | 做法 | 影响 |
|---|---|---|
| **A. ETF 收益代理**（推荐） | 行业指数 `10-15 收盘 = 10-14 收盘 × (1 + 对应 ETF 当日收益)`；个股/ETF 缺当天数据的行业，用同层中位收益 | 沿用既有 tier③ 口径（`docs/数据兜底-实时行情补尾部.md`），只新增一根 bar |
| B. 等源端补发 | 什么都不做，等申万补 10-15 | 零风险；但源端若不补，这一天永久缺失 |

补 A 之后必须做的事（本次 10-15 就是按这套走的；注意到期日会**提前一个日历日**）：
① 把日期写进 `config.GAP_FILL_DATES` 并从 `KNOWN_JUDGE_GAPS` 删掉；
② 重建 `etf_panel`（`build_etf_panel.py`）；
③ 全量重放 `ark.py daily --full`；
④ 结论数/年化/到期日的差异写进本文档。

## 六、怎么复查

```bash
python3 engine/ark.py status     # 末尾「判断层日历缺口」一节（已登记 · / 未登记 ✗）
python3 engine/ark.py verify     # 未登记缺口 → 失败；两层日历不一致 → 失败
```

三种动作，一一对应：

| 情况 | 要改哪里 |
|---|---|
| 新出现一个洞，决定**暂不补** | 在 `config.KNOWN_JUDGE_GAPS` 加一行（日期 + 证据），verify 即通过 |
| 决定**补**这一天 | 在 `config.GAP_FILL_DATES` 加工日期 → 重建 `etf_panel` → `daily --full` |
| 源端**补发**了官方值 | 无需动作：`overwrite_est` 会用真值覆盖 est 行；随后把该日期从 `GAP_FILL_DATES` / `KNOWN_JUDGE_GAPS` 删掉 |

判断"这是不是一个洞"的标准证据（四个数字缺一不可）：

```bash
# ① 申万该日有几只指数（应为 0/120）
# ② 全池 ETF 该日有几只有行情（应为几十~120/123）
# ③ 上证指数该日是否有收盘（有 = 市场开市）
# ④ 基准交易日里该日是否在 panel 里（不在 = 判断层缺这天）
```

源端补发或决定补数据后，**务必删掉登记条目**，否则守卫会永远认为这一天"不必管"。
