# 「我的持仓」打开 ETF 弹窗的口径：按入市起始日算本账户的真账

日期：2026-09-24　　涉及：`web/src/{sim,etf-modal,etf-modal-host,MyBook}.ts(x)`

## 一、问题：同一个弹窗，两种账

「标的走势核验弹窗」（`etf-modal.tsx`）原本只有一个数据源：`review.json` 的
`settlement.events`，也就是**引擎自己的账本**——初始本金 1.0（归一化）、
从 2018 年回测起点开始跑、金额是按目标权重折算出来的名义值。

但「我的持仓」页显示的是**另一本账**（`sim.ts: runSim`）：按**你填的本金与入市起始日**
在浏览器里逐日重放引擎的资金规则。两本账并不等价：

- 引擎账本在 2024-12-31 那天**已经持仓**；你设「入市起始日 = 2024-12-31」则是
  那天**拿全额现金重新起账**。现金不同 → 建仓金额不同 → 槽位占用不同 →
  **之后买的标的与时点都会分叉**；
- 于是弹窗画出来的 B/S 点，和页面上「当前持仓」表里的笔数对不上——
  同一个页面上两套买点，用户无法逐笔核对。

所以弹窗在「我的持仓」里必须换数据源，而不是换个标签。

## 二、变更：`open()` 支持「本账户口径」的覆盖

```ts
// 复盘页 / 今日研判页（不变）：引擎名义账本口径
open(sid, focusDate?)

// 我的持仓页：本账户口径
open(sid, focusDate, {
  events: bookEvents(acct, sid),                                  // 本账户在该标的的 B/S
  scope: { from: acct.startDate, to: acct.asOf,                   // 入市起始日 → 选中日
           capital: acct.capital, realMoney: true },
  curve: { dates: acct.window.map(w => w.d),                       // 账户总值（元）
           nav:   acct.window.map(w => w.v) },
})
```

`sim.ts` 新增两样东西：

- `SimResult.buys / .sells`：入市起始日以来的**全部成交**（含已平仓；
  `positions` 只是其中尚未到期的那些）。每笔带 `wShare`（占账户总值比例，
  与 `settlement.py` 事件的 `w_share` 同一算式）、`amt`（实际付出/成本）、
  `sh`（实际份数）、`proceeds`、`pnl`（已扣双边成本的真钱）；
- `bookEvents(acct, sid)`：把上述成交转成弹窗要的 B/S 事件（复权价口径与图上一致）。

## 三、弹窗在「本账户口径」下的表现

| 位置 | 引擎口径（复盘/今日研判） | 本账户口径（我的持仓） |
|---|---|---|
| 顶部 | 无 | 「『我的持仓』口径统计：入市起始日 … → 盯市至 …」 |
| ETF 涨跌卡 | 数据起点 → 最新交易日 | **入市起始日 → 选中日** |
| 已结算卡 | 系统已结算 N 笔 · 名义 1 万/笔 | **本账户已结算 N 笔 · 已实现盈亏（真钱）· 累计投入成本** |
| 在途卡 | 名义 1 万/笔的平均浮动 | **成本 → 市值 → 浮动盈亏（元）** |
| 图 | 全部引擎 B/S | **只有本账户的 B/S**（其他事件不画） |
| 账本表 | 固定名义本金 1 万元 → 份额 → 卖出金额 → 结算 ret 对账 | **买入金额 / 份数 / 卖出金额 / 已实现盈亏（元）** |
| 账本表·在途行 | 有（到期日按交易日历 + 建议周期推算，超出数据末端标 `~`） | 有（到期日取自重放账本，含 `~` 推算标记） |
| 悬浮「组合净值」 | 引擎归一化净值 | **账户总值（元）**，取自本账户资金曲线 |
| 初始视窗 | 末端往前 240 个交易日 | **窗口内**（窗口更长时取窗口末端往前 240 日） |

### 入市起始日 = 你填的那一天

重放原本把曲线基点放在**起始日的前一交易日**，于是填 2026-09-01、弹窗显示 2026-08-31。
现在基点落在**起始日本身**（非交易日顺延到下一交易日，页面已有此提示）：

- 本金在起始日**收盘入账**，该日收盘的结论在**下一交易日开盘**首次建仓——
  与全系统「T 收盘出结论 → T+1 开盘买入」一致，所以弹窗里的第一个 B 点可能晚于起始日一天；
- 顺延后的日期就是 `acct.startDate`，弹窗与页面各处显示的都是它；
- 起始日**晚于全部数据**（如选了未来日期）时不再静默退到数据末端，而是明确显示
  「尚未开始跟随」。选「选中日当天」则账户已开始、账本为空（第一次建仓在下一交易日）。

### 「选中日」= 账户盯市日；走势数据必须更到同一天

卡片上写「2026-09-01 → 2026-09-23（入市起始日 → 选中日）」，其中**选中日 = 账户的盯市日**
（`acct.asOf`，就是页面上那个「我的持仓 · 日期」）。它曾经显示成 09-21，原因不是口径，
而是**数据陈旧**：

- 弹窗的走势/价格序列来自 `web/public/view/etf/<sid>.json`（**展示层**，2026-09-24 之前
  在 `web/public/data/etf/`），由 `engine/build_etf_webdata.py` 从结算账簿切片而来；
- 这份导出**不在** L0→L3 的重建依赖链上（数据层推不动它），`ark.py daily` 当时只重建
  ETF 面板、不重建走势文件 → 走势停在最后一次手工运行的那天（09-21），
  而账户用的 `sim.json` 已经到 09-23；
- 修复三层：① `ark.py daily` / `init` 显式跑 `build_etf_webdata.py`（现在排在管线**之前**，
  因为它只依赖 `cache/etf_panel.json`，这样管线写 review.json 时展示层已是最新）；
  ② `_index.json` 记录日期轴末端 `last`，`ark.py status` / `verify` 把它当成
  **展示层陈旧守卫**（`VIEW_etf_modal`），参与「各层应当同日」的校验，不一致直接失败；
  ③ 卡片在该标的**选中日确实没有行情**（停牌/退市/缺口）时，把范围写成
  「入市起始日 → 该标的最后一个行情日；选中日 X 无该标的行情」。

重建后同一只 0.159516 的卡片从「2025-01-02 → 2026-09-21，+215.29%」变为
「2025-01-02 → 2026-09-23，+212.67%」——多算了两个交易日，在途估值也从 09-21 收盘价
换成 09-23 收盘价。

### 复权参照必须与结算层同源（否则两处市值对不上）

「当前持仓」里 159516 一行写 市值 ¥51,461 / 浮动 +¥3,399（+7.07%），
弹窗却写 本账户在途持仓 +¥5,586 / 市值 ¥53,649——同一批 12 笔、同一成本 ¥48,062，
差在**估值价**：页面用 `sim.px.c`（结算取价）2.891，弹窗用走势文件的 `adj` 3.0142。

根因是**份额折算复权的参照不同源**（`engine/qfq.py`）：

| 调用方 | 参照 | 该标的两个断点的因子 | 2026-09-23 复权价 |
|---|---|---|---|
| `pipeline.load_etf_book()`（结算 + 账户重放） | 申万**行业指数**（`ref_src=index`） | ×2.01223、×2.001182 | **2.89127** |
| `build_etf_webdata.py`（弹窗走势） | 传了 `None` → 退化成**全池中位数**（`ref_src=median`） | ×1.946177、×2.157059 | 3.014177 |

两者差了 4.2%——正好是用户看到的市值差。更糟的是弹窗还会显示
`cache/qfq_report.json` 里落盘的因子（那是 `qfq.py` 单独运行时的产物），
于是「图上标出的复权因子」和「红线实际乘的因子」互相矛盾。

修法（2026-09-24 起升级为「唯一来源」，见下节）：

- `build_etf_webdata.py` 改成与 `load_etf_book()` **同一调用**：传申万面板、
  用 `C.QFQ_BREAK_THRESH`；
- 断点清单直接用本次复权返回的报告，不再读落盘文件——**显示的因子必须就是乘进 adj 的那个**；
- `ark.py verify` 新增「弹窗走势与结算取价一致性」：对 `sim.json` 里每只结算标的
  抽查最近 3 个有价日，`etf/<sid>.json` 的 `adj` 必须与 `px.c` **逐位相同**，
  不一致直接失败（已实测：把某日复权价人为改 1% 即被拦下）。

### 2026-09-24：改成「展示层只消费结算账簿」（上面那版仍不够）

上面那版是把两份实现**改得一致**（都传申万参照），但仓库里仍然存在**两份复权实现**：
结算层走 `pipeline.load_etf_book()`（尊重 `config.ETF_QFQ`，也尊重 `ARK_QFQ=0` 开关），
展示层直接调 `qfq.apply_qfq()`（**无视该开关**）。只要哪天有人把 `ETF_QFQ` 关掉做对照实验，
结算立刻变回不复权价、弹窗还是复权价——红线再次拉开，而且这次是靠 `verify` 事后发现。

改法（结构性消除，而不是靠校验兜）：

- `pipeline.load_etf_book(with_report=True)` 返回 `(book, breaks)`；
- `build_etf_webdata.py` **不再 import qfq、不再读 panel.json 做复权**，只做
  「取字段 + 切片成 per-sid 小文件」：`adj`/`breaks` 来自上面那一次调用，
  `raw`/名称/行业映射来自 `cache/etf_panel.json`（L1 原样，不复权）；
- 产物迁出数据层目录：`web/public/data/etf/` → **`web/public/view/etf/`**
  （独立展示层根，镜像到 `site/view/`），前端三处 fetch 改为 `view/etf/…`；
- 水位层改名 `L3_etf_webdata` → **`VIEW_etf_modal`**，定位为「展示层陈旧守卫」而非数据层水位；
- `_etf_webdata_vs_settlement()` 保留，但语义从「可能踩的坑」变成**回归断言**：
  拦的是「以后有人给展示层加回一套自己的复权实现」。

迁移验收：新旧产物 **125/125 个文件逐字节相同**（`json.dumps(sort_keys=True)` 比对），
与 `sim.json` 的 `px.c` 逐位一致（0 处不一致）。即"改了结构、没改数值"。

修完，同一批持仓两处数字完全一致：

```
页面（按 ETF 汇总）  12 笔 | 成本 ¥48,062 | 市值 ¥51,461 | +¥3,399（+7.07%）
弹窗（本账户在途）   12 笔 | 成本 ¥48,062 → 市值 ¥51,461 | +¥3,399 / 浮动 +7.07%
```

顺带修正了一个被掩盖的数字：「入市以来 ETF 涨跌」在跨断点区间（如 2025-01-02 → 2026-09-23）
原本用的是中位数因子，现按结算口径重算，由 +212.67% 变为 **+199.92%**。

### 账本明细含「在途」行



原表只列**已卖出**的配对（以 S 事件为准），手里的持仓在表里看不见。
现在每一条买入都有一行：已结算行 = 有 S 的配对；**在途行 = 有 B 无 S**（浅底 + 「在途」标签）。

在途行的每一格都写清楚它是估值而不是成交：

| 列 | 在途行的取值 |
|---|---|
| 卖出日 | 「在途」标签，悬浮给到期日（`~` = 按周末推算，未计节假日） |
| 卖出价 / 卖出金额 | 按窗口末端收盘价估的值，带「估」字 |
| 毛收益率 | 浮动收益率，带「浮动」字样 |
| 成本 / 净收益率 | `—`（还没卖出，双边成本尚未发生） |
| 已实现 / 浮动盈亏 | **浮动盈亏**（本账户口径为真钱；引擎口径为名义 1 万元账本的浮动） |
| 卖出原因 | `未平仓 · 到期日 …` |

在途行的到期日：本账户口径直接取重放账本里的 `endDate`（与「我的持仓」的到期日列同源）；
引擎口径没有该字段，用交易日历按 `买入日索引 + 建议周期` 推算（与结算层 `end = buy_i + H` 同规则），
超出数据末端则按周末推算并标 `~`。

窗口过滤是双保险：调用方给的事件已经是本账户的，弹窗仍会再按
`from ≤ date ≤ to` 过滤一遍——万一将来有人用引擎事件配窗口，也不会把
入市之前的成交算进来。在途持仓的估值价也取「≤ 选中日的最后一个复权价」，
所以卡片上的「估值截至」可能早于选中日（ETF 数据比账户日历晚一天时），如实标出。

**一处刻意留白**：本账户重放不带基准序列，所以悬浮里不显示「相对基准超额」
（引擎事件有该字段才显示）。宁可不显示，也不拿别的东西冒充。

## 四、实测校验

**等价性**（新口径没有改变引擎口径）：把本金设为 1、入市起始日留空——此时重放
与引擎账本应当逐笔一致。实测（headless Chrome，点开逐一核对）：

| 标的 | 引擎 B / S | 账本行数（B） | 已结算行（S） | 在途行（B−S） | 已结算行的买入日集合 |
|---|---|---|---|---|---|
| 0.159516 半导体设备ETF国泰 | 16 / 12 | 16 ✓ | 12 ✓ | 4 ✓ | 与引擎卖单的买入日完全一致 |
| 1.512480 半导体ETF国联安 | 35 / 30 | 35 ✓ | 30 ✓ | 5 ✓ | 与引擎卖单的买入日完全一致 |

**窗口生效**：本金 10 万、入市起始日 2025-01-02 时，同一只 0.159516 从
12 笔已结算缩为 **8 笔**、在途 4 笔不变，ETF 涨跌窗口从
「2023-07-27 → 2026-09-21」变为「2025-01-02 → 2026-09-21」；
入市起始日 2026-09-01 时该标的只剩在途 12 笔（本账户在该日之后建的仓）。

**边界**：起始日 = 选中日当天 → 账户已开始、账本为空（首次建仓在下一交易日）；
起始日 = 周六 → 顺延到下一交易日；起始日晚于全部数据 → 显示「尚未开始跟随」。

**未回归**：复盘页弹窗仍为「ETF 累计涨跌（复权）· 数据起止」「系统已结算 · 名义 1 万/笔」
与「ret 对账 ✓」列；全流程 0 未捕获异常。

## 五、顺带统一的 UI

「我的持仓」表格里的 ETF 名称此前用的是无样式的 `span.etflink`（黑色纯文本），
与今日研判页的 `EtfLink`（`.linkbtn.etf-link`：蓝色 + 下划线）不一致。现已改用同一套
类名与排版（名称加粗可点、代码灰色跟随），六张表（买入/候选/卖出/持仓/对账）全部一致。
