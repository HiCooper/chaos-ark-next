# 混沌方舟 ARK — 架构评审（2026-10-02）

> 评审目标（用户口径）：**系统架构清晰有组织且易拓展；备注详略得当；数据分层设计易高效增量更新。**
> 方法：只读评审。盘点目录 / 模块依赖图 / 行数 / 数据体量 / 文档引用关系，逐条给出证据；
> **未修改任何代码与配置**。本文档本身是本次评审的唯一产物。

---

## 〇、总评

这套架构的**数据工程部分是超规格的**——write-once 不可变 L0、canary 自证的增量重放、
水位即验收，这三件在同类个人量化项目里罕见，在机构项目里也未必做到。真正的短板不在设计
而在**治理**：三个新 L0 kind 游离在水位体系外、engine/ 平铺 64 个文件让生产面和实验面
不可分、docs 里 40% 的复现命令指向已删除的脚本、运行依赖一个仓库外的 venv。

**目标对照记分卡**：

| 目标 | 评分 | 一句话判断 |
|---|---|---|
| 数据分层 · 高效增量更新 | **9 / 10** | L2/L3 增量已是标杆；扣分在 L0 抓取全量重下与新 kind 无生命周期 |
| 代码组织 · 易拓展 | **6 / 10** | 生产链本身干净（schema 解耦、配置单源）；扣分在目录混居、无索引、复现失效 |
| 备注详略得当 | **8 / 10** | config.py 是范本；扣分在「行为型注释」会随口径过期（已发生过 3 处） |

## 二、做得好的（明确建议：保持，勿动）

1. **L0 write-once + manifest sha256**（`rawstore.py`）：不可变语义、est 行可被官方值覆盖的
   唯一例外、「禁止手改 L0」的纪律。这让 351M 原始数据成为唯一需要保护的东西，其余皆可重建。
2. **增量重放的正确性是自证的，不是假设的**：两条硬不变式（float64 落盘 / 窗口起点锚定
   `window_start`）+ canary 尾部比对（不一致自动退化为全量并告警）。`--tail 12` 的增量
   因此是**可信的快**，快速路径整条管线 CPU ≈ 56s。
3. **水位即验收**：`status` 是「更新到哪天」的唯一口径；`daily` 前后对比水位并检查 site 同步；
   `verify` 把 L0 完整性、登记簿合规、账本独立重放、弹窗=结算取价全部断言掉。
4. **config.py 的注释范式**：每个参数都带「依据 + 日期 + 复现命令」，参数的来龙去脉可考。
   这是「备注详略得当」的现行最佳实践，应作为其他模块的标尺。
5. **rules.py 前端零硬编码**：页面上的参数、规则、分层数字全部由引擎导出，改参数不需要碰前端。
6. **sync_site 的删除语义**：内容不同的才复制（sha256 比对），源里没有的目标里删掉——
   「宁可少一个文件，不留淘汰文件在线上」，这是对的。
7. **工程细节有思考痕迹**：`_run` 不用 PIPE 防无人值守场景的读端阻塞死锁；
   `pick_python` 找不到解释器时给出可执行指引而不是裸报错。

## 三、发现的问题与改进建议（按优先级）

### P1-1 三个新 L0 kind 游离在治理体系之外 【数据分层 · 最重要】

**证据**：`sw_valuation`（71M）/ `analyst_rank`（192M）/ `sw_component`（744K）于 2026-09-29
一次性抓取后——
- `docs/DATA-LAYERS.md` 的 L0 表**没有它们**（表里只有 catalog / sw_index / bench / etf /
  kline_em / manifest）；
- `ark.py` 的 `water_level()` / `status` / `verify` 对它们**零覆盖**（grep 无一命中）；
- 不在任何定时链路里，也没有「应当多久更新一次」的声明。

这不是功能 bug（它们对现行管线惰性），而是**生命周期没有 owner**：三个月后没人回答
「analyst_rank 停在几号、还能不能用」，而它占着 L0 一半以上的体量（263M / 351M）。

**建议**（两步，都便宜）：
1. `DATA-LAYERS.md` L0 表补三行（kind、来源接口、体量、抓取命令、当前区间）；
2. 给 `water_level()` 加一段「非管线 kind」扫描：列出 `data/raw/` 下所有目录及其最后落盘
   日期，与管线水位并列展示。存量陈旧度一旦可见，接不接入 daily 就有了决策依据。
   （若决定接入，做成 `daily --with-fundamentals` 可选段，注意申万接口 page_size≈200 的坑。）

### P1-2 engine/ 平铺混居 + 复现命令失效率 40% 【代码组织】

**证据**：64 个 .py 单目录平铺，生产 ≈20 个 vs 一次性 ≈41 个混在一起；「哪个文件属于
生产面」这个问题目前只能靠读 ark.py 源码回答。更硬的证据：docs 里引用的 `engine/*.py`
路径共 40 个（去重），其中 **16 个已不存在**（lab_dd / lab_diag / lab_grid×6 / lab_opt×6 /
oos_b / verify_parity）——**实验文档的复现命令失效率 40%**，且没有任何机制会发现这一点。

**建议**（分三步走，尊重「文档即证据」的项目哲学）：
1. **立即（零风险）**：写 `engine/README.md` 索引——三栏表「生产链 / 实验台 / 诊断」，
   每行一句话说明 + 对应 docs 出处。让 `ls engine/` 的认知成本从 64 降到 20。
2. **短期（新约定，不动存量）**：新实验脚本统一进 `engine/lab/`（历史脚本不动，保证旧文档
   命令仍可复现）；diag 类新脚本进 `engine/attic/` 或直接不写（结论进 docs，脚本当天删）。
3. **中期（可选，一次性迁移）**：把 30+8 个存量实验/诊断脚本 `git mv` 进 `engine/lab/`，
   同步在 docs 加一行「2026-10-02 前的旧路径为 engine/xxx.py」。成本约半小时 + 文档声明；
   收益是生产面永久干净。**做不做取决于你对「历史文档命令逐字可跑」的执念程度**——
   本项目方法论强调可复现，建议保留旧路径可跑（即选方案 2）为主案。

### P1-3 report/ 历史快照无防误用标识

**证据**：`report/ark_rules_spec.py` 与 `ARK_买卖规则_交叉验证.md` 抬头标注
`engine_version = ark-1.1.0-etf`，但内容里的 `[60,80,100]`、`回退 H=20`、`min_days=20 共 3 笔`
都是 1.1.0 时代的事实；同时 **2026-09-29 的两份实验文档仍引用它作为权威依据**
（`ark_rules_spec.py:272` 佐证 avoid_crowd_pct 是死配置）。将来有人把它当现行规格书会出错。

**建议**：给 `report/` 加一个 `README.md`（两行）：「本目录为 ark-1.1.0-etf 时代的交叉验证
快照，仅供历史核对；现行参数以 `engine/config.py` 与 `docs/DATA-LAYERS.md` 为准。」

### P2-1 无测试防线（有验收，无回归）

**证据**：全仓无 tests/。核心不变式都靠「事后验收」（verify / canary / lab_flex verify），
但它们不拦截「下次改动引入的回归」——例如 qfq 断点还原、rawstore write-once 语义、
结算器与影子模拟器的逐位一致性，目前都没有改动即触发的检查。

**建议**：加 `python3 engine/ark.py selftest`（贴合现有 CLI 习惯，不引入 pytest 依赖），
收录五个快测（全部 <1min）：
1. 结算器 parity：把 `lab_flex.py verify`（自证与生产 nav 逐位相等）提升为可调用检查；
2. qfq：构造含已知断点的合成序列，断言还原值；
3. rawstore：临时目录 put 两次，断言首采值保留、est 可被官方值覆盖；
4. `lab_registry check`（已有，纳入）；
5. config 合法性（BASE_WEIGHTS 权重和、HORIZON_CANDIDATES 有序去重等）。
触发时机：改 settlement / qfq / rawstore / config 之后手动跑一次，或并进 verify 的快速段。

### P2-2 settlement.py / review.py 巨石（机会主义拆分，勿专门重构）

settlement 1,194 行里混了四种角色：`EtfBook` 数据结构、`simulate_cash_account` 账户模拟、
`build_exposure_cap` 等风控辅助、`market_phases` 分段。**不建议为美学专门重构**——
重放不变性是本项目的命根子，动它必须付全量比对的成本。建议：
- 现在只做一件事：在模块 docstring 写「分区地图」（哪段是什么职责，便于导航）；
- 立规矩：下次因功能需要触碰时顺手拆出 touched 部分，拆完必须过
  「day 文件逐字节一致 / nav 逐位一致」再提交。

### P2-3 生产运行依赖仓库外的 venv

**证据**：`requirements.txt` 存在且 `ark.py init` 本会建 `.venv`，但本机从未建过——
`pick_python()` 兜底落到 WorkBuddy akshare skill 的 venv（`~/.workbuddy/skills/akshare-data/.venv`）。
这是个**环境巧合**：skill 升级/卸载的那一刻 daily 就挂，且报错路径会让未来的自己困惑。

**建议**：跑一次 `python3 engine/ark.py init`（或 `python3 -m venv .venv && pip install -r
engine/requirements.txt`），让 pick_python 的第一顺位命中。零代码改动。

### P2-4 运行日志落在 /tmp

**证据**：`_run` 把子进程日志写到 `/tmp/ark_<name>_<ts>.log`。/tmp 在重启后清空，
而「27 分钟那次 daily 到底慢在哪」这类事后归因恰恰需要跨天日志。

**建议**：改写到 `cache/logs/`（已在 .gitignore 的 cache/ 范围内，不污染仓库），
并保留最近 N 份的简单清理。一行级改动。

### P3-1 L0 抓取是全量重下（已知成本，暂不建议动）

**证据**：`datasource_sw.py --refresh` 每日全量重下 162 个指数全历史再 merge-append，
是 daily 15-20 分钟里的主要成本（2026-09-30 实测约 13min，当日异常 27min 属数据源侧波动）。
并行抓取受 akshare 限频约束（项目记忆里有限频坑位记录），收益不确定。

**判断**：write-once + 全量重下的鲁棒性是**刻意选择**（merge-append 语义简单可证），
56s 的管线 CPU 说明瓶颈只在网络。**除非日更耗时成为实际痛点，否则保持现状**；
若将来要动，优先级是「交易日历短路（节假日直接跳过抓取）」>「分批并行」>「按日期增量拉取」。

### P3-2 命名考古学（低优先级）

diag / diag2 / diag3 / diag_2024 / diag_gate / diag_gate2、lab_downyear…downyear5 这类
「版本号后缀」命名无法自解释。约定：一次性脚本用**日期后缀**（docs 的现行约定），
不用数字后缀；diag 类结论写进 docs 后脚本即可删（登记簿记录其存在与去向）。

## 四、对照三个目标的结论

### 4.1 数据分层 · 高效增量更新（9/10，收益最大的动作是 P1-1）

分层设计本身（含「展示层为什么不是 L4」的论证、两条重放不变式、canary 兜底）是这套系统
最强的资产，**不需要重新设计，需要补治理**：把三个手动 kind 纳入水位可见范围，
「增量」的主链（L2/L3 --tail + canary + sha256 镜像）已经无可指摘。

### 4.2 代码组织 · 易拓展（6/10，收益最大的动作是 P1-2）

易拓展的真实支撑点已经存在——「下游只认 schema 不认来源」（换数据源不改下游）、
config 单源、engine_version/config_hash/panel_fingerprint 链。缺的是**入口的可知性**：
新人（或半年后的自己）打开 engine/ 需要 15 分钟才能分清生产与实验。
engine/README.md 索引 + 新脚本进 lab/ 两个动作就能把 6 分拉到 8 分。

### 4.3 备注详略得当（8/10，收益最大的动作是立「注释三律」）

config.py 证明了这个项目完全会写注释（依据+日期+复现命令三件套）。已暴露的风险是
**「描述现行行为」的注释会随口径漂移**——2026-10-02 刚修掉 3 处（horizon.py 的 10/20/40/60
与过期状态向量、lab_stage_horizon 的 [60,80,100]）。建议把三条约定写进
`docs/实验记录规范.md`：
1. **行为型注释引用常量，不写死数字**（「见 C.HORIZON_CANDIDATES」优于「80/100 日」）；
2. **依据型注释必带日期与出处**（现行做法，保持）；
3. **写「为什么」优先于「是什么」**（代码本身已表达「是什么」）。

## 五、建议执行顺序（全部为独立小项，无依赖耦合）

| 序 | 动作 | 规模 | 风险 |
|---|---|---|---|
| 1 | `ark.py init` 建项目 venv（P2-3） | 一条命令 | 无 |
| 2 | `report/README.md` 防误用标识（P1-3） | 两行 | 无 |
| 3 | `engine/README.md` 生产/实验/诊断索引（P1-2 步1） | ~60 行 | 无 |
| 4 | `DATA-LAYERS.md` 补三个 kind + `water_level()` 报告非管线 kind（P1-1） | 半小时 | 低（只加显示，不加行为） |
| 5 | 日志 /tmp → cache/logs/（P2-4） | 十行 | 低 |
| 6 | `ark.py selftest` 五项快测（P2-1） | 半天 | 低 |
| 7 | 注释三律写入实验记录规范（4.3） | 十行 | 无 |
| 8 | 实验脚本目录迁移（P1-2 步3，可选） | 半小时+文档声明 | 中（破坏旧命令路径） |

> 1-7 均不改变任何计算口径，不触碰重放不变性；8 是唯一有权衡的项。
