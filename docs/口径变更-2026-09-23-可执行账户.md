# 口径变更：结算层改为「有限资金池的可执行账户」（ark-1.8.0-executable）

日期：2026-09-23　版本：`ark-1.7.2-cash-1pct` → **`ark-1.8.0-executable`**

## 一、变更原因：净值曲线隐含了「每日再平衡」

旧口径的收益式是

```
r_raw = Σ(当日收益ᵢ × wᵢ) / Σwᵢ            # w = (1/σ) × (综合分/50)^0.5，每天重算
r     = expo × r_raw + (1 − expo) × rf      # expo = 波动目标暴露系数
```

`w` 每天重新计算并重新归一化，数学上**等价于每个交易日收盘把全部持仓再平衡回目标权重**——
卖掉涨多的、买入跌多的。但：

- 事件日志里只有「建仓 / 到期卖出」，没有任何调仓单；
- 成本只在开仓与平仓时收一次，这份每日调仓**完全免费**；
- 现金没有约束：仿佛卖出总能瞬间完成、总有资金可投。

结果是**两本账**：事件层与「当日出手」描述的是「只买 + 到期卖」，净值层走的却是
「每日免费再平衡」，后者把回撤从 −34.8% 美化到 −21.4%（同一批成交，只换记账口径）。
实盘做不到：资金池有限、不会每天卖出再平衡。

## 二、新口径：现金账户逐日记账（`settlement.simulate_cash_account`）

- **资金**：初始本金一笔钱，此后**卖出所得是唯一资金来源**；未投入部分按现金收益率计息
  （2026-09-23 晚已把 `cash_yield` 改为 0，见第十三节）。
- **建仓**：T+1 开盘买入，金额 = `min(账户总值 × 入场闸门 ÷ K, 可用现金)`，
  预算再按 `1/σ × (综合分/50)^tilt` 倾斜；`K = PORTFOLIO.target_positions`（目标持仓笔数，默认 16）。
- **卖出**：默认只有「持有到建议周期结束」当日收盘卖出；所得现金供后续建仓。
- **权重**：建仓后**随价格自由漂移，不再被拉回目标**——系统内不存在任何形式的每日再平衡。
- **时序**：① 开盘买入（只用昨收现金）→ ② 收盘卖出（**当日所得次日可用**）
  → ③ 现金计息 → ④ 收盘盯市。当日到期的持仓当日开盘仍占槽位。
- **风控**：波动目标 / F5 暴露上限只作用于**新仓预算的闸门**，**无法降低存量暴露**；
  要降必须显式卖出，本口径不采用。
- **净值**：`账户总值 = 现金 + Σ 持仓市值`，由记账产生，不再由公式给定。

## 三、验收：账本可执行性对账（新增硬校验）

`engine/verify_ledger.py`（已接入 `ark.py verify`）：只用产物（事件日志 + 价格），
独立重放一本现金账，逐日与发布净值对比。判定：最大相对偏差 < 5e-04 且现金 ≥ 0。

当前结果：最大偏差 **4.46e-05**、最低现金 0.000034、事件 572 条 / 2111 个交易日 → **通过**。
任何隐含交易（例如再平衡）都会立刻放大成数量级偏差，使 verify 直接失败。

这条校验是本次事故的直接补丁：以前的三层核验（价格对账 / 双路径复现 / 无前视）
全部在同一个错误前提下自洽，没有一条检查「这本账拿现金能不能执行」。

### 4. 页面结构调整：先回答「今天买什么、卖什么」

原版按**记账时序**切成「当日已执行」「下一交易日待执行」两段，用户得自己拼出"我要做什么"。
现在「我的持仓」页的顺序是：① **今天要做什么**（要买入几笔/合计多少钱、要卖出几笔/合计多少钱，
再逐笔列出金额、约合手数、持有周期）→ ② 账户概览 → ③ 当前持仓 → ④ 对账（当日已成交，不需要操作）。

配套修掉两个真问题：

- **最后一天的结论被引擎丢掉了**。它的买入日（T+1）在数据之外，`trades_exec` 的 open_edge
  会跳过（`i0 + 1 >= len(book.dates)`），因此影子账户在**最新交易日**（最常用的情形）显示"没有候选"。
  现在 `build_sim_export` 显式补入最后一天的结论（σ 用截至最后一天的数据，无前视），
  与末日计划块同一口径 → sim.json 的信号日 543 → 544。
- **下一交易日不在数据里**时，页面按周末推算日期（标 `~`：到期日同理），
  并注明"节假日以交易所公告为准"；数据中段的选中日则用真实日期。

另外：槽位满/现金不足时不再只说"不能买"，而是给出**排队候选**（按综合分排序、
含"若现在有槽位时的预算"）与**最早腾出槽位的到期日**——用户仍然知道系统下一步想做什么。

## 十四、页面时间轴：什么时候知道、什么时候执行（2026-09-23 晚）

问题（用户提出）：**「9.23 的结论要等 9.23 收盘后才出，那 9.23 盘中要做什么，我怎么会知道？」**

答案分两层：

1. **信息本身不缺**：执行日 E 的操作单来自**上一交易日 D 收盘**的结论——D 晚上就发布了，
   所以 E 开盘前一定拿得到。缺的从来不是数据，而是页面有没有把"结论日 / 执行日"讲清楚。
   因此「我的持仓」页顶部新增**时间轴**：

   ```
   结论日（已发布） 2026-09-23  收盘后生成 · 2026-09-23 22:10:55；它决定下一交易日的买卖
   执行日（今天）   2026-09-24  盘中（买入按开盘价成交；卖出按收盘价成交，收盘前完成）
   下一份结论       2026-09-24 收盘后  约 15:05 起可用申万实时行情兜底出当日结论
   ```

2. **页面按执行日说话**（`execStateOf`，用浏览器本地日期判断，纯函数、可单测）：

   | 客户端日期 vs 执行日 | 页面口吻 |
   |---|---|
   | 执行日未到（结论日晚间 / 周末） | 「**{执行日}（下一交易日）要做什么**」：现在就能把单子定下来 |
   | 执行日当天 | 「**今天（{执行日}）要做什么**」，并按盘中时点提示：开盘前可挂单 / 盘中（买在开盘、卖在收盘）/ 已收盘 |
   | 执行日已过而新结论未出 | 时间轴标红「已过去 N 天，新的结论还没出」+ 黄色警示条：给出最近一份可用结论对应的操作单（标注"已过期，仅供补做/核对"）与补跑命令 |

   操作单表格（买入金额/约合手数/占组合/持有周期；卖出金额/参考盈亏）来自影子账户对执行日
   的重放；下方「对账：{结论日}已成交」是**结论日当天**真实发生的买卖，二者不再混在一栏。

**结论**：真正的风险只有"数据没跟上"（申万指数未出数、或当天没跑 daily），而不是"盘中信息不可知"。
前者由第十二节的实时兜底（收盘后几分钟即可出当日结论）+ 本节的滞后台账共同兜住：
页面既告诉你该做什么，也告诉你手里这份结论是不是最新的。

### 3. 别把「有结论但建不了仓」的信号藏掉

2026-09-23 的结论给出 1 笔埋伏（半导体设备），但影子账户当时已 32/32 满仓，
于是「下一个交易日操作」只剩一句"槽位已满"——**信号被页面吃掉了**（精简时间轴时把候选表弄丢了）。
现在买入区在被挡下时固定显示：

```
今日结论给出的建仓候选（1 笔）：下一交易日开盘按金额买入；名额或现金一释放，就按综合分从高到低建仓
  半导体设备ETF国泰159516  半导体设备  埋伏  68.8  ¥9,079（有名额时）  31 手  100 日
```

金额列按被挡的原因切换：槽位满 → 「买入金额（有名额时）」取预算；现金不足 → 「按可用现金可买」取 min(预算, 现金)。

### 4. 「下一个交易日操作」的金额曾可能超过可用现金

2026-09-16 用户发现：页面显示下一交易日买入 ¥8,885，而可用现金只有 ¥7,324。
原因在前端**投影**（不是引擎）：候选按综合分逐笔算 `min(预算, 现金)`，但每一笔都用**同一份
全部现金**封顶、没有逐笔扣减，于是两笔的合计可以超过手里的钱（实测近 260 个交易日里有 36 天命中，
例：现金 ¥7,160 却报买入合计 ¥8,458）。

修复：投影与候选队列都改成**逐笔扣减可用现金**，与引擎真实建仓的 `cash -= amt` 完全同规则。

两条回归断言（`node` 里跑同一份 sim.json）：

- **投影 == 实际**：D 页面投影出的"下一交易日买入"必须与引擎重放到 D+1 时的"当天真实成交"
  逐笔一致（标的 + 金额，4 位小数）——3 档本金 × 500 个交易日 = 1497 例，**0 例不一致**；
- **不超支**：任何一天的买入合计 ≤ 当时可用现金——4 档本金 × 400 天，**0 例超支**。

顺带确认：修完后「JS 重放 vs 引擎」在 2022-01-04 起点仍逐位一致（期末 0.899330 对 0.899330，
最大偏差 5.0e-06；注意该基线要用 `cash_yield=0` 的引擎版本重算，1% 的旧基线已作废）。
